# Fullbleed 2.4.0 release runbook

Status: candidate; dedicated PDF/VT validation pending

Release from the exact annotated `v2.4.0` tag after all gates pass. Do not create
the production tag or publish immutable registry artifacts while the dedicated
PDF/VT gate is unverified.

## Release contract

- Cargo, Python, CI, README installation examples, generated artifacts, and release metadata must report 2.4.0.
- `fullbleed_audit_contract` remains 0.1.3. `fullbleed-mcp` remains 0.1.0; its installed-core delegation accepts `fullbleed>=2.3.0,<3`.
- Wheels retain CPython 3.10–3.14 ABI3 compatibility across the 15-platform matrix, and Rust MSRV remains 1.85.
- Generate `fullbleed-agent-contract.json`, `cli_schema.md`, and `llms.txt` from the final installed wheel. Rebuild so packaged `agent_contract.json` and `llms.txt` match the repository artifacts; `cli_schema.md` remains repository documentation.
- Preserve qualified PDF/VT-oriented language until exact-specimen independent validation evidence exists. Private DPM and reuse hints do not establish interoperability or performance.

## Local source and installed-package gates

Use an isolated Python environment for the release wheel and test tools.

```powershell
cargo fmt --all --check
cargo test --locked
cargo test --locked --features python,svg_raster
cargo check --locked --all-targets --all-features
python tools/check_release_metadata.py --expected-version 2.4.0 --json
python tools/check_license_integrity.py --json
python build_backend/fullbleed_build_backend.py wheel --out target/release-2.4.0/dist
python -m pip install --force-reinstall target/release-2.4.0/dist/fullbleed-2.4.0-cp310-abi3-win_amd64.whl
python tools/generate_agent_contract.py --python python --json
python build_backend/fullbleed_build_backend.py wheel --out target/release-2.4.0/dist
python build_backend/fullbleed_build_backend.py sdist --out target/release-2.4.0/dist
python tools/generate_agent_contract.py --python python --check --json
python tools/generate_mcp_server_json.py --check --json
$env:FULLBLEED_TEST_INSTALLED_NATIVE = "1"
python -m pytest -q
python tools/smoke_installed_package.py --expected-version 2.4.0 --json
python goldens/run_golden_suite.py --python python verify
python tools/generate_css_parity_status.py --check --json
python -m twine check target/release-2.4.0/dist/*
rustup run 1.85.0 python tools/smoke_crates_consumer.py --expected-version 2.4.0 --json
cargo publish --locked --dry-run
```

Validate the bundled Skill using the local Skill validator and the GitHub
`gh skill publish --dry-run` workflow described in `docs/agent-discovery.md`.
Retain raw test, package, and deterministic-output evidence. Review the final
diff, then run `tools/check_release_worktree.py` from the clean release commit.
See [the candidate validation report](2.4.0-validation-report.md) for retained
local evidence and the unresolved publication gate.

## Dedicated PDF/VT release gate

Both `release.yml` and `publish-crates.yml` require
`.github/workflows/pdfvt-release-gate.yml` before publication. Configure:

| Repository variable | Required value |
| --- | --- |
| `PDFVT_VALIDATOR_RUNNER` | JSON array of labels for the runner with a usable dedicated validator |
| `PDFVT_VALIDATOR_CMD` | Command template selecting PDF/VT-1 validation, with `{pdf}` and optional `{report}` |
| `PDFVT_VALIDATOR_VERSION_CMD` | Command reporting product version and selected validation profile |
| `PDFVT_OUTPUT_INTENT_ICC` | Path to the real sRGB ICC used for the retained specimens on that runner |

The command must normalize exit codes: 0 for conformance, 1 for nonconformance,
2 or higher for configuration/tool errors. The gate executes without a shell.
Do not configure a mock, an internal inspection command, or a PDF/X-only
validator as the dedicated PDF/VT validator.

The harness checks five positive VT specimens, three negative controls,
internal parsed contracts, PDF/X-4 validation, and replay determinism. It
retains raw reports, PDFs, input/artifact hashes, and validator-version output
in the `pdfvt-release-evidence` workflow artifact. Download those artifacts
and preserve them with the release evidence after the CI retention period.

Local equivalent, once a dedicated validator is available:

```powershell
python tools/validate_pdf_profiles.py --profile pdfx4 --profile pdfvt1 --install-pdf-oxide --strict-external --require-dedicated-pdfvt --out target/release-2.4.0/pdfvt-evidence
```

Also run the broader PDF/A, PDF/UA, and WTPDF harness with veraPDF when verifying
those profile claims. A successful internal or PDF/X-only run does not close
the dedicated PDF/VT gate.

## Publish and verify

1. Retain successful evidence for the final source and built wheel; change candidate status only when the release gates have passed.
2. Commit and push the source, then create and push annotated `v2.4.0`.
3. Let the tag-triggered Release workflow validate and assemble all 15 wheels and the sdist.
4. Dispatch `publish-crates.yml` for `v2.4.0` with `publish=true`.
5. Dispatch `release.yml` at `v2.4.0` with `publish_pypi=true`.
6. Create the GitHub release from `ReleaseNotes.MD`, attaching distributions and a SHA-256 manifest.
7. Verify crates.io and PyPI versions, MIT metadata, unyanked status, exact artifact hashes, and the matching tagged source. Install the public wheel in a fresh environment and run version, doctor, compliance, and installed-package smoke checks.
