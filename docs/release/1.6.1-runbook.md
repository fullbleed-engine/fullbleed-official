# Fullbleed 1.6.1 Release Runbook

This runbook builds and validates the `v1.6.1` source state through
`.github/workflows/release.yml`, publishes the complete Python distribution
set to PyPI, and publishes the two MIT-licensed Rust crates through the
crates-only `.github/workflows/publish-crates.yml` workflow.

## Supported Python Contract

Fullbleed 1.6.1 supports standard CPython 3.10, 3.11, 3.12, 3.13, and 3.14.
The extension targets `abi3-py310`, so each platform wheel has a
`cp310-abi3` tag and is installable across that interpreter range.

Release artifacts cover:

- manylinux 2014 x86-64, x86, ARM64, ARMv7, s390x, and ppc64le
- musllinux 1.2 x86-64, x86, ARM64, and ARMv7
- Windows x86-64, x86, and ARM64
- macOS Intel and Apple silicon
- source distribution

Free-threaded CPython builds and prerelease Python 3.15 are not part of the
1.6.1 support contract.

## One-Time Registry Setup

Create two protected GitHub environments:

1. `crates-io`
2. `pypi`

The `crates-io` environment only permits the default branch to run the manual
publisher. The publisher checks out, validates, and publishes the exact commit
behind the annotated `release_tag` input. Add required reviewers if the
repository's release policy uses manual approval.

For crates.io trusted publishing, add the following GitHub Actions publisher
to both the `fullbleed` and `fullbleed_audit_contract` crate settings:

- Owner: `fullbleed-engine`
- Repository: `fullbleed-official`
- Workflow: `publish-crates.yml`
- Environment: `crates-io`

No long-lived crates.io token is stored locally or in GitHub. The workflow
requests a short-lived OpenID Connect credential only in the protected publish
job, and the official authentication action revokes it when the job ends.

For PyPI trusted publishing, configure the existing `fullbleed` project with:

- Owner: `fullbleed-engine`
- Repository: `fullbleed-official`
- Workflow: `release.yml`
- Environment: `pypi`

No PyPI API token is required. The publish job requests an OpenID Connect
identity token only after every distribution and wheel smoke gate succeeds.

## Local Release Candidate Checks

Run from a clean checkout:

```powershell
python -m pip install "maturin==1.14.1" "twine==7.0.0" pytest
python tools\check_release_metadata.py --expected-version 1.6.1 --json
python tools\check_license_integrity.py --json
cargo fmt --all --check
cargo test --locked
cargo test --locked --features python,svg_raster
python -m pytest -q
python -m maturin build --release --locked
python -m maturin sdist --out dist
python -m pip install twine
python -m twine check target\wheels\* dist\*
```

Inspect the Cargo package file sets:

```powershell
cargo package --locked --list --manifest-path crates\fullbleed_audit_contract\Cargo.toml
cargo package --locked --list
```

`fullbleed_audit_contract` 0.1.1 must be published before the Rust
`fullbleed` 1.6.1 crate.
Until 0.1.1 exists in the crates.io index, Cargo can list the main package but
cannot complete `cargo package` or `cargo publish --dry-run`: registry
dependency resolution correctly reports that only 0.1.0 is available. After
0.1.1 propagates, run `cargo publish --locked --dry-run` for the main crate.
The crates-only publish workflow enforces this ordering, waits for index
propagation, and then performs Cargo's full package verification while
publishing `fullbleed`.

Both Fullbleed-authored crates declare `MIT`, embed the same MIT `LICENSE`, and
are rejected by the workflow if that metadata changes. Dependencies retain
their own licenses; they do not change the MIT license on Fullbleed-authored
source.

## Dry Run in GitHub Actions

Run the `Release` workflow manually with `publish_pypi` left false. It will:

1. validate version and MIT metadata;
2. run Rust and Python tests and package both crates;
3. build 15 platform wheels and the source distribution;
4. install and exercise every wheel on its native architecture or under QEMU;
5. install the manylinux x86-64 wheel on Python 3.10 through 3.14;
6. verify the complete platform set, distribution metadata, and
   `cp310-abi3` tags;
7. retain the complete artifacts without publishing.

Download `release-dists` and `cargo-packages` from the workflow run for final
inspection. Before the first 0.1.1 publication, `cargo-packages` contains the
verified audit-contract crate and the main crate's package file listing.

Run the `Publish crates.io` workflow with `release_tag=v1.6.1` and `publish`
left false. It independently validates the annotated tag, MIT metadata, Rust
tests, audit-contract package, and main-crate file set without publishing.

## Build From the Release Tag

1. Confirm the release commit is clean and all local checks pass.
2. Push the exact release commit.
3. Create and push the annotated tag:

   ```powershell
   git tag -a v1.6.1 -m "Fullbleed 1.6.1"
   git push origin v1.6.1
   ```

4. Confirm the tag-triggered workflow builds and smoke-tests all 15 wheels and
   the source distribution.
5. Download `release-dists`, run `python -m twine check` over every file, and
   publish the complete set to PyPI in one upload.

Cargo publishing is available only through an explicit `Publish crates.io`
manual dispatch with `release_tag=v1.6.1` and `publish=true`, after trusted
publishers are configured for both crates. PyPI publishing is a separate
`Release` dispatch with `publish_pypi=true`. A tag push alone never publishes
registry packages. Published registry files are immutable and must never be
overwritten.

## Post-Publish Verification

In fresh environments:

```powershell
cargo info fullbleed@1.6.1
cargo info fullbleed_audit_contract@0.1.1
python -m pip install --no-cache-dir fullbleed==1.6.1
python -m fullbleed --version
python -m fullbleed doctor --strict --json
python -m fullbleed compliance --strict --json
```

Confirm that both Cargo packages and PyPI report the MIT License and that PyPI
selects a `cp310-abi3` wheel on every supported CPython version.
